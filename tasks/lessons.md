# Lessons

[2026-08-01] `git pull -- <valeur>` ne protège PAS contre l'injection de flags, contrairement à `git fetch -- <valeur>` ou `git diff -- <valeur>`. `git pull` transmet l'argument à son appel interne de `git fetch` sans préserver le séparateur `--`, donc une valeur du type `--upload-pack='cmd'` reste interprétée comme un flag et exécute la commande. Règle : pour tout outil qui doit encapsuler `git pull` de façon sûre avec un remote contrôlé par l'utilisateur/l'agent, le décomposer en `git fetch` (protégé par `--`) + `git merge --ff-only FETCH_HEAD` plutôt que de guarder `git pull` directement. Toujours vérifier empiriquement qu'un `--` guard fonctionne réellement sur la sous-commande git visée — ne pas supposer que le comportement se propage aux appels internes.

[2026-08-01] Les reviews de tâches isolées (spec + qualité par tâche) peuvent chacune approuver un module alors qu'une vulnérabilité transversale (ex: un seul outil sur 14 non protégé) leur échappe. La review finale holistique sur tout le diff après toutes les tâches est ce qui a détecté ce problème — ne jamais sauter cette étape sur du code touchant à la sécurité (subprocess, shell, injection).

[2026-08-01] Ne jamais accepter le rapport d'un subagent implémenteur sur un correctif de sécurité sans le faire vérifier indépendamment par un autre subagent qui reproduit lui-même l'exploit avant/après. Dans ce cas, l'implémenteur avait dévié de la correction suggérée (une ligne) vers une réécriture plus profonde (fetch+merge) — la vérification indépendante a confirmé que cette déviation était justifiée et non du scope creep.

[2026-08-02] Un test suggéré par un plan peut avoir une assertion no-op qui passe toujours, ex. `assert Path(folder) / ".openagent" / "memory.md"` — un objet `Path` est toujours truthy (pas de `__bool__` custom), donc ce test ne vérifie RIEN, ni l'existence du fichier ni son contenu. Règle : toute assertion nue sur un objet (pas une comparaison, pas un `.exists()`/`.method()`) dans un test suggéré par un plan doit être lue comme suspecte par défaut — vérifier qu'elle peut réellement échouer avant de la garder telle quelle.

[2026-08-02] Pour une mémoire persistante réinjectée dans chaque conversation future (fichier markdown relu à chaque session), un `append_*` qui écrit quand même une entrée horodatée vide quand l'appelant passe des faits vides/blancs est un vrai defect d'ergonomie, pas juste un edge case théorique : ce bruit s'accumule silencieusement au fil des appels d'outil LLM (ex. `save_memory(facts="")`) et pollue le contexte de toutes les sessions suivantes. Règle : pour tout store append-only destiné à être relu automatiquement, traiter un append de contenu vide/blanc comme un no-op explicite, pas comme un cas à laisser passer tel quel.

[2026-08-02] Un module de contexte relu à chaque tour de conversation (`project_memory.py`) doit dégrader gracieuement sur les erreurs I/O (`try/except OSError: return ""` en lecture, `pass` en écriture), pas juste sur "fichier absent" — un `PermissionError` (antivirus, éditeur qui a le fichier ouvert, écriture concurrente) est un `OSError` réel et fréquent sur Windows, et le laisser se propager transforme un simple accès mémoire raté en crash de tout le tour de conversation. Règle : avant d'implémenter un module `context/*.py` lu à chaque tour, vérifier le pattern de dégradation gracieuse déjà établi dans les modules siblings (ici `project_instructions.py`) et le répliquer — ne pas le découvrir seulement en code review. Même leçon pour `newline="\n"` explicite sur les écritures texte : `crud_tools.py` le fait déjà partout, `Path.write_text` sans ce paramètre laisse Windows appliquer la traduction CRLF (round-trip Python-only, mais incohérent avec le reste du codebase) — vérifier les conventions déjà établies dans les modules voisins avant d'écrire du nouveau code, pas seulement les tests suggérés par le plan.

[2026-08-02] Un `forget_*`/suppression sélective sur un store append-only horodaté (`memory.md` avec des blocs `<!-- timestamp -->`) ne doit jamais filtrer ligne par ligne sur un mot-clé — un fait peut s'étaler sur plusieurs lignes, et ne supprimer que les lignes matchant le mot-clé laisse soit un en-tête horodaté orphelin (aucune ligne de contenu derrière), soit des fragments du même fait qui n'ont plus de sens isolés. Règle : pour tout store dont l'unité logique est un bloc délimité (ici un marqueur `<!-- timestamp -->`), une suppression doit opérer au niveau du bloc entier (découper sur le délimiteur, filtrer les blocs, réassembler), jamais au niveau de la ligne — sinon la commande de suppression corrompt silencieusement la structure au lieu de simplement retirer un fait obsolète.

[2026-08-02] Un test de régression générique — "tout outil de `_ALL_TOOLS` doit être classé dans `_RESTRICTED_TOOLS` ou `_READ_ONLY_TOOLS`" — écrit en réaction à la leçon du plan précédent (git-dev-tools : outils git non classés découverts en review finale) a immédiatement détecté une lacune préexistante et sans rapport avec la tâche en cours : `fetch_url`, enregistré dans `agent.py` bien avant cette tâche, n'était classé nulle part. Règle : quand une classe de bug s'est déjà produite deux fois dans le même projet (permissions.py ici), écrire le test de garde générique correspondant plutôt que de re-vérifier manuellement à chaque nouvelle tâche — le test générique attrape aussi les instances historiques, pas seulement les nouvelles.
