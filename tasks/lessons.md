# Lessons

[2026-09-14] | Les premiers tests du nouveau stockage ont montré que `null` servait à la fois de valeur JSON et de sentinelle « fichier absent », autorisant un reset silencieux de coffre/conversation. Règle : distinguer l'absence physique avec `undefined`, valider toute valeur lue (y compris null), et tester la conservation exacte des fichiers invalides avant la migration.

[2026-09-14] | L’audit npm a signalé Electron 38.8.6 vulnérable ; la mise à jour vers 44.3.0 a été bloquée par le quota d’exécution escaladée. Règle : ne pas déclarer le paquet distribuable quand la version corrigée n’est pas installée et l’audit pas relancé.

[2026-09-14] | Le prototype Electron conservait un processus Python, omettait les réglages globaux et remplaçait plusieurs actions NiceGUI par des boutons sans implémentation équivalente. Règle : avant une migration d'interface/runtime, inventorier les gestionnaires et les services historiques dans une matrice de parité, distinguer interface et moteur, puis exiger une preuve clic → effet → persistance pour chaque fonction et un lancement du paquet sans l'ancien runtime avant d'annoncer la migration livrée.

[2026-09-13] | Le défaut `folder='.'` d'un nouvel outil d'initialisation visait le dossier de lancement même lorsqu'un autre projet était actif dans l'UI (reproduit par deux tests RED). Règle : pour les outils projet utilisés par GUI et CLI, résoudre dossier explicite → dossier actif → cwd, et couvrir ces chemins avec de vrais fichiers. L'écriture exclusive `x` protège la création des collisions sans imposer les hard links, indisponibles sur certains volumes; conserver temp + `os.replace` pour les écrasements autorisés.

[2026-09-13] | Une table de priorité dont le commentaire promet « lockfiles avant manifests » peut rester incohérente dès qu'elle mêle plusieurs écosystèmes : vérifier seulement les collisions internes (pnpm contre npm) ne détecte pas `package.json` placé avant un lockfile Python. Règle : pour toute sélection par artefacts mixtes, séparer la politique en strates exhaustives (tous les lockfiles, puis tous les manifests) et ajouter au moins un test de collision inter-écosystèmes.

[2026-09-13] | Le scan projet gérait déjà les erreurs d'énumération (`os.walk`/`iterdir`) mais pas l'échec de `Path.is_dir()` ou `Path.is_file()` sur une entrée obtenue juste avant — une permission peut changer entre ces deux opérations. Règle : pour tout résumé fondé sur une liste de `Path`, garder un `try/except OSError` autour de chaque métadonnée de chaque entrée, pas seulement autour de l'énumération initiale.

[2026-08-01] `git pull -- <valeur>` ne protège PAS contre l'injection de flags, contrairement à `git fetch -- <valeur>` ou `git diff -- <valeur>`. `git pull` transmet l'argument à son appel interne de `git fetch` sans préserver le séparateur `--`, donc une valeur du type `--upload-pack='cmd'` reste interprétée comme un flag et exécute la commande. Règle : pour tout outil qui doit encapsuler `git pull` de façon sûre avec un remote contrôlé par l'utilisateur/l'agent, le décomposer en `git fetch` (protégé par `--`) + `git merge --ff-only FETCH_HEAD` plutôt que de guarder `git pull` directement. Toujours vérifier empiriquement qu'un `--` guard fonctionne réellement sur la sous-commande git visée — ne pas supposer que le comportement se propage aux appels internes.

[2026-08-01] Les reviews de tâches isolées (spec + qualité par tâche) peuvent chacune approuver un module alors qu'une vulnérabilité transversale (ex: un seul outil sur 14 non protégé) leur échappe. La review finale holistique sur tout le diff après toutes les tâches est ce qui a détecté ce problème — ne jamais sauter cette étape sur du code touchant à la sécurité (subprocess, shell, injection).

[2026-08-01] Ne jamais accepter le rapport d'un subagent implémenteur sur un correctif de sécurité sans le faire vérifier indépendamment par un autre subagent qui reproduit lui-même l'exploit avant/après. Dans ce cas, l'implémenteur avait dévié de la correction suggérée (une ligne) vers une réécriture plus profonde (fetch+merge) — la vérification indépendante a confirmé que cette déviation était justifiée et non du scope creep.

[2026-08-02] Un test suggéré par un plan peut avoir une assertion no-op qui passe toujours, ex. `assert Path(folder) / ".openagent" / "memory.md"` — un objet `Path` est toujours truthy (pas de `__bool__` custom), donc ce test ne vérifie RIEN, ni l'existence du fichier ni son contenu. Règle : toute assertion nue sur un objet (pas une comparaison, pas un `.exists()`/`.method()`) dans un test suggéré par un plan doit être lue comme suspecte par défaut — vérifier qu'elle peut réellement échouer avant de la garder telle quelle.

[2026-08-02] Pour une mémoire persistante réinjectée dans chaque conversation future (fichier markdown relu à chaque session), un `append_*` qui écrit quand même une entrée horodatée vide quand l'appelant passe des faits vides/blancs est un vrai defect d'ergonomie, pas juste un edge case théorique : ce bruit s'accumule silencieusement au fil des appels d'outil LLM (ex. `save_memory(facts="")`) et pollue le contexte de toutes les sessions suivantes. Règle : pour tout store append-only destiné à être relu automatiquement, traiter un append de contenu vide/blanc comme un no-op explicite, pas comme un cas à laisser passer tel quel.

[2026-08-02] Un module de contexte relu à chaque tour de conversation (`project_memory.py`) doit dégrader gracieuement sur les erreurs I/O (`try/except OSError: return ""` en lecture, `pass` en écriture), pas juste sur "fichier absent" — un `PermissionError` (antivirus, éditeur qui a le fichier ouvert, écriture concurrente) est un `OSError` réel et fréquent sur Windows, et le laisser se propager transforme un simple accès mémoire raté en crash de tout le tour de conversation. Règle : avant d'implémenter un module `context/*.py` lu à chaque tour, vérifier le pattern de dégradation gracieuse déjà établi dans les modules siblings (ici `project_instructions.py`) et le répliquer — ne pas le découvrir seulement en code review. Même leçon pour `newline="\n"` explicite sur les écritures texte : `crud_tools.py` le fait déjà partout, `Path.write_text` sans ce paramètre laisse Windows appliquer la traduction CRLF (round-trip Python-only, mais incohérent avec le reste du codebase) — vérifier les conventions déjà établies dans les modules voisins avant d'écrire du nouveau code, pas seulement les tests suggérés par le plan.

[2026-08-02] Un `forget_*`/suppression sélective sur un store append-only horodaté (`memory.md` avec des blocs `<!-- timestamp -->`) ne doit jamais filtrer ligne par ligne sur un mot-clé — un fait peut s'étaler sur plusieurs lignes, et ne supprimer que les lignes matchant le mot-clé laisse soit un en-tête horodaté orphelin (aucune ligne de contenu derrière), soit des fragments du même fait qui n'ont plus de sens isolés. Règle : pour tout store dont l'unité logique est un bloc délimité (ici un marqueur `<!-- timestamp -->`), une suppression doit opérer au niveau du bloc entier (découper sur le délimiteur, filtrer les blocs, réassembler), jamais au niveau de la ligne — sinon la commande de suppression corrompt silencieusement la structure au lieu de simplement retirer un fait obsolète.

[2026-08-02] Un test de régression générique — "tout outil de `_ALL_TOOLS` doit être classé dans `_RESTRICTED_TOOLS` ou `_READ_ONLY_TOOLS`" — écrit en réaction à la leçon du plan précédent (git-dev-tools : outils git non classés découverts en review finale) a immédiatement détecté une lacune préexistante et sans rapport avec la tâche en cours : `fetch_url`, enregistré dans `agent.py` bien avant cette tâche, n'était classé nulle part. Règle : quand une classe de bug s'est déjà produite deux fois dans le même projet (permissions.py ici), écrire le test de garde générique correspondant plutôt que de re-vérifier manuellement à chaque nouvelle tâche — le test générique attrape aussi les instances historiques, pas seulement les nouvelles.

[2026-08-02] Convertir une fonction en `async def` sur une event loop mono-thread (NiceGUI) introduit deux classes de bugs distinctes, pas une seule : (a) un `await` cède le contrôle, donc tout état mutable lu *après* l'await peut avoir changé entre-temps si un autre gestionnaire d'événement s'exécute pendant l'attente — snapshotter TOUT ce qui doit rester cohérent (y compris la "queue" qu'on comptait relire après coup) en une seule fois, avant l'await, jamais en deux lectures séparées de part et d'autre ; (b) sans garde de ré-entrance explicite, une fonction async déclenchable depuis plusieurs points d'entrée (bouton manuel + déclenchement automatique) peut s'exécuter deux fois en concurrence, ce qui aggrave (a) et peut dupliquer des écritures persistantes (ici `append_to_project_memory`). Règle : pour toute fonction `async def` qui mute un état partagé et est atteignable depuis plus d'un point d'appel, ajouter systématiquement (1) un flag de ré-entrance vérifié en entrée avec retour anticipé + notification, remis à `False` dans un `finally` couvrant tout le corps y compris les retours anticipés internes, et (2) un unique snapshot pré-await de tout ce qui sera réassemblé post-await.

[2026-08-02] Un `try/except` trop large autour d'un appel LLM asynchrone — qui englobe aussi les effets de bord post-succès (refresh UI, notify) — transforme un échec bénin de UI-refresh en un message d'erreur trompeur ("LLM indisponible") alors que l'appel LLM a en réalité réussi et que l'état a déjà été persisté. Règle : le `try` doit être resserré au strict minimum (l'appel réseau/LLM + l'extraction du résultat) ; toute mutation d'état, persistance et notification de succès doit vivre en dehors de ce bloc, pour qu'un échec de UI ne soit jamais rapporté comme un échec du travail qui a réussi.

[2026-08-02] Un bloc `if summary:` sans `else` sur un résultat potentiellement vide (résumé LLM vide) est un no-op totalement silencieux côté utilisateur : aucun changement d'état, aucun refresh, aucune notification — le seul signal visible (un toast "en cours…") disparaît tout seul sur son propre timer, laissant croire que tout s'est bien passé. Règle : tout chemin de sortie précoce sur un résultat vide/inattendu d'un appel LLM/outil doit avoir une notification explicite dédiée, jamais un simple passage sous silence du bloc de traitement normal.

[2026-08-02] Un chemin de fichier global (`~/.openagent/...`) défini comme **constante de module** calculée à l'import (`GLOBAL_X_PATH = Path.home() / ...`) plutôt que comme fonction est une bombe à retardement pour les tests : rien n'empêche `monkeypatch` de cibler une constante déjà résolue, donc tout test qui exerce le chemin global (y compris implicitement, via un appel avec `project_folder=None` ou une fonction qui boucle sur les deux portées) lit/écrit le vrai `~/.openagent/` du poste de développement. Ce bug s'est reproduit une deuxième fois dans ce même plan (`context/learnings.py` suggéré par le plan, après `project_memory.py` en Task 1) — c'est maintenant une classe de bug connue pour tout module `context/*.py` à portée projet+globale. Règle : dès qu'un module a une portée globale basée sur `Path.home()`, exposer systématiquement `_global_<x>_path() -> Path` comme fonction (jamais une constante), et écrire au moins un test qui pointe explicitement `Path.home()` vers un `tmp_path` vide (sans monkeypatcher la fonction elle-même) pour vérifier qu'aucune exception n'est levée et que rien n'est lu du vrai poste — pas seulement monkeypatcher la fonction dans les tests qui l'utilisent directement.

[2026-08-02] Injecter du contexte système via des messages `{"role": "system", ...}` poussés dans l'état d'un graphe LangGraph est un mécanisme **mort** dans ce codebase, et l'était déjà avant ce plan : `trim_message_history` (`context/messages.py:33`) fait `non_system = [m for m in messages if not isinstance(m, SystemMessage)]` — il supprime *inconditionnellement* tout SystemMessage entrant à chaque tour, puis `agent_node` réinjecte un unique SystemMessage construit uniquement depuis `system_prompt` + `load_project_instructions(cwd)`. Trois fonctionnalités successives (custom_prompt de dossier — antérieur au plan —, injection mémoire de la Task 3, injection learnings de la Task 5) ont donc été chargées, formatées, préfixées à l'historique… et jetées avant d'atteindre le LLM, sans la moindre erreur visible. Chacune était "testée" (formatage pur testé unitairement) et review-approuvée en isolation. Règle : pour toute fonctionnalité dont l'effet est « le LLM doit voir X », le test qui compte n'est PAS un test de formatage de X, c'est un test qui capture ce qui arrive réellement à `model.invoke(...)` et vérifie que X s'y trouve. Corollaire : quand un pipeline transforme des messages entre l'appelant et le modèle (trim, clean, compat), lire ce pipeline en entier avant de croire qu'un contenu ajouté en amont y survit — et se méfier d'un mécanisme d'injection qui *diffère* du mécanisme déjà éprouvé dans le même fichier (`project_instructions` était, lui, chargé directement dans `agent_node` : c'était le modèle à copier, pas à contourner).

[2026-08-02] Un `build_agent()`/factory d'agent qui binde *toujours* la surface d'outils complète transforme n'importe quel appel LLM auxiliaire en surface d'exécution non gardée. Ici la compaction (`context_bar.trigger_compact`) appelait `build_agent(mode="ask", ...)` sans `permission_manager` : `mode` ne fait que changer une phrase de prompt (advisory) et ne restreint *aucun* outil, et le `permission_manager=None` faisait tomber `build_graph` sur un `ToolNode(_ALL_TOOLS)` nu — donc `run_command`/`delete_file`/`git_push` exécutables sans confirmation, automatiquement, sur une entrée dérivée de l'historique de conversation (donc de contenu web/fichiers potentiellement porteur d'une injection de prompt). Règle : un appel LLM purement transformationnel (résumer, classer, reformuler) doit être construit avec une surface d'outils **vide**, pas simplement « avec permissions » — un gate qui auto-autorise les outils read-only reste du risque pour zéro bénéfice. Et un paramètre de "mode" qui n'agit que sur le prompt ne doit jamais être lu comme une restriction de capacités.

[2026-08-02] Un `bind_tools([])` n'est pas équivalent à « pas d'outils » : il pose `tools: []` dans la requête, que certains providers rejettent, et masque l'intention derrière un bind vide. Idem côté graphe, l'ordre des branches de sélection du nœud d'outils compte : tester `permission_manager is not None` avant `tools` permettait à une liste vide + un manager de produire quand même un `ToolNode`. Règle : « liste d'outils vide » doit court-circuiter en premier, à la fois le bind (`model.bind_tools(tools) if tools else model`) et le câblage du nœud (`if not tools: noop`), pour qu'une surface vide soit structurellement inexécutable plutôt que dépendante de l'ordre des conditions.

[2026-08-02] Deux bugs trouvés en review qualité sur `context/learnings.py` (commit b653d44, corrigés en ef8db6c) :

[2026-08-06] Un plan (Task 3, plan artifacts-content) suggérait un composant factory (`render_prompt_picker`) qui crée un `ui.dialog()` comme variable locale de sa propre closure et ne retourne que le `ui.button` associé — puis, dans le même plan, un autre fichier (`input_bar.py`) appelant `prompt_dlg.open()` sur une variable jamais définie nulle part. Le bug était détectable par simple lecture croisée des deux snippets du plan (Step 4 vs Step 5), sans exécuter quoi que ce soit. Règle : quand un plan fait créer un objet UI/état dans la closure d'une fonction A puis fait référencer cet objet par son nom depuis un site d'appel B, vérifier explicitement que A retourne bien un moyen d'atteindre cet objet (l'objet lui-même, ou une méthode liée dessus) — ne pas supposer qu'un identifiant qui apparaît des deux côtés d'un plan est forcément câblé entre les deux. Corrigé en faisant retourner à la factory un tuple `(widget, callable_lié)` plutôt que le seul widget, pattern à réutiliser pour tout futur composant popup/dialog déclenché depuis un autre module.

[2026-08-06] Deux bugs trouvés en review qualité sur `exporter.py` (Task 4, commit e5e2438, corrigés en c92dd88) :

[2026-08-06] Bug Critique trouvé en review qualité sur `input_bar.py`/`chat.py` (Task 5 plan artifacts-content, commit 4f77ed07, corrigé en 64820bd) : `edit_message(idx)` (tronque `state.messages` pour restaurer un ancien message dans l'input) n'avait aucun garde sur `state.agent_running`, contrairement à sa fonction sœur `regenerate()` qui en a un juste au-dessus dans le même fichier. [2026-08-07] Bug Critical trouvé en audit holistique final (7 tâches, plan artifacts-content) : une feature d'état DÉRIVÉ en mémoire (`state.branches`/`current_branch_id`, Task 7) peut être correcte pour tout son propre code, et pourtant se faire écraser silencieusement par un mécanisme de PERSISTANCE PRÉEXISTANT qui n'a aucune notion de ce nouvel état. Ici `save_chat_history(folder, state.messages)`, appelée sans garde après chaque tour dans `input_bar.py::_send_message` (préexistante à la feature branching), écrivait sur disque n'importe quelle vue active — y compris une branche, dont le contenu est une version tronquée/divergente de "main". Résultat : envoyer un message sur une branche écrasait `chat_history.json` avec ce contenu partiel, perdant définitivement tout ce qui suit le point de fork sur main, sans erreur ni avertissement. Règle : quand une feature introduit un état "vue active parmi plusieurs" (branches, onglets, modes d'affichage) qui remplace la même variable partagée qu'un mécanisme de persistance/sync/export préexistant lit sans discrimination, grep TOUS les lecteurs de cette variable partagée (pas seulement les nouveaux sites que la feature ajoute elle-même) — un `state.messages` (ou équivalent) qui change de "propriétaire logique" au cours du temps rend dangereux tout code plus ancien qui le lisait en confiance comme une source unique de vérité. Corollaire réutilisable : une fonction non-testable en isolation (couplée à NiceGUI/LLM, comme `_send_message`) ne doit pas rester un obstacle à écrire un test de régression réel sur son garde critique — extraire le garde dans une petite fonction dédiée (ici `_save_main_chat_history()`) est le compromis correct, à condition que la fonction extraite exécute exactement la même logique de production que celle appelée par le code non testable, pas une réplique séparée.
